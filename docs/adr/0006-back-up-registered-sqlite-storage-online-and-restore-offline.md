# Back up registered SQLite storage online and restore it offline

Ronin backs up every durable service database through one explicit `storage-databases.json` registry and SQLite's Online Backup API. The registry identifies each database by a stable logical ID, filename inside the private data volume, schema version, code-known schema-SQL fingerprint, size ceiling, no-audio classification, and exact set of application-owned SQLite objects. The expected fingerprint rejects changed table or index definitions even when their names and `user_version` are unchanged. Storage administration never walks the data directory or accepts arbitrary source paths. Adding another durable service database requires adding its descriptor to the registry; a backup is incomplete and rejected unless it contains the complete current registry set.

Each published artifact is owner-only and content-addressed by a bounded manifest. The manifest binds the Hex storage service identity, build revision, complete registry digest, and each standalone database's size, SHA-256, schema version, and schema fingerprint. Backup validation runs SQLite integrity and foreign-key checks. Artifacts contain retained transcripts and credential digests and therefore remain sensitive, but they contain no Captured Audio because audio is never persisted and no unregistered path can enter the artifact.

Restore is an offline operator action. The wrapper must stop the proxy and Parakeet and prove every prior container is neither running, paused, nor restarting before invoking the restore adapter. The adapter validates the complete artifact before mutation, restores all databases into a staged directory through the Online Backup API, preserves the prior main databases and SQLite sidecars in an owner-only recovery directory, then installs and revalidates the new main files. A durable restore marker blocks service storage startup across interruption. A failed replacement rolls the old files back and removes only the device-reauthorization gate created by that failed attempt; a gate that predated the attempt is preserved. A failed rollback or gate cleanup keeps a startup gate and recovery state fail-closed.

A successful restore leaves both services stopped. Restoring the device registry also rolls credential and revocation state back to the artifact snapshot, so restore first creates a durable device-reauthorization startup gate and invalidates any proof from an earlier attempt. The offline wrapper then revokes every restored principal and records that reset before it reports success. Clearing the gate requires a fresh health-only service principal whose credential is the actual Compose-mounted host health secret plus a distinct fresh non-service dictation principal; old and partially restored credentials cannot resume traffic. The ordinary verified deploy remains the only authority that rotates the Parakeet process epoch and starts traffic. CI must prove production startup fails on both restore gates, an idempotent response retained before backup is served as a replay after restore, exact-schema tampering is rejected, and a single manifest restores multiple databases.
